# ADR 0012: Text-mode fallback / server-driven display

Status: Proposed (owner request 2026-11-25)

## Context

The master's HDMI output needs something sensible when the selected target
has no video (no capture yet in phase 1, DUT off, unlocked source). The owner
also wants the Linux server to be able to put arbitrary status text on the
monitor. It must cost only a few BRAMs and no frame buffer.

## Decision

* **Mode**: 80 × 25 character cells, 8 × 16 font (9-pixel cells as VGA text,
  720 px wide), rendered into a 720 × 480 @ 60 Hz (27 MHz; was 576p50, changed by issue 0027) DVI/HDMI raster,
  text area centred (88 lines top/bottom). Same mode as the MEGA65 PAL output
  so switching between text and pass-through does not change monitor mode.
* **Memory** (one per supervisor, not per DUT):

  | Range | Size | Contents |
  |---|---|---|
  | 0x0000–0x07CF | 2000 B | characters (CP437), row-major |
  | 0x0800–0x0FCF | 2000 B | attributes: low nibble foreground, high nibble background |
  | 0x1000–0x102F | 48 B | palette: 16 × RGB888 |
  | 0x1030 | 1 B | control: b0 force text display, b1 blink enable |

  Chars and attributes: 2 × BRAM18 (2 KiB each); palette in LUTs; font
  4 KiB in one BRAM36 (Terminus-derived CP437 8×16 from hardweb, SIL OFL 1.1).
  A 256-colour (RGB332) attribute mode was considered; 16 colours with a
  loadable 24-bit palette gives exact colours for less memory and keeps a whole
  screen in one jumbo frame.
* **Wire format**: UDP port **6508**, common header type **0x50 TEXT_WRITE**,
  payload `addr u16, reserved u16, data…`; bytes are written to consecutive
  addresses from `addr`. A full screen + palette + control is one 4145-byte
  payload (jumbo); without jumbo frames the host sends chunks (e.g. ≤ 1400
  bytes each). No acknowledgement; the host simply repeats/refreshes.
* **Fast path**: a small tap in the `clk_rx` domain (`text_rx_tap`) parses
  the Ethernet/IPv4/UDP/custom header of every frame as it arrives (dst MAC =
  either endpoint MAC, IPv4 without options, UDP dst 6508, magic/version/type)
  and from payload byte 4 onward writes each byte straight into the text BRAMs
  at line rate. No buffering and no FCS check: a corrupt frame may leave
  wrong characters until the next refresh, which is acceptable for a display.
  The normal slot path ignores port 6508 frames.
* **When shown**: whenever the selected video target has no valid source
  (phase 1: always), or when the control byte forces it. Phase 3 muxes the
  same renderer with pass-through video at frame boundaries.
* **Default content** at power-up (before the server writes anything): a
  status screen generated by the FPGA (board DUT IDs, IPs, link) is phase 2+;
  phase 1 shows a fixed banner from the BRAM init values.

DHCP sequencer are adapted from the owner's hardweb project
