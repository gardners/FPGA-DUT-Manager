# Mimas A7 networked hardware test farm

**Architecture and detailed design — working draft 0.5, 25 November 2026**

Status: reviewable engineering handoff; not a validated schematic or final wire-protocol specification. Requirements marked **Agreed** reflect the discussion; **Proposed** identifies implementation choices for review; **Open** identifies a decision or experiment still required. The intent is to minimise FPGA logic, hardware purchases and cabling, not to reproduce a commercial KVM feature set.

## 1. Purpose and scope

Provide remote, independent control of real MEGA65 and HewnWeb prototype hardware for development, interactive use and automated regression testing. Use the two existing full-sized, pre-V4 Numato Mimas A7 (A50T-class, actual FPGA marking to verify) boards, expanding to four supervisors and eight DUTs. Each supervisor handles two DUTs for JTAG, UART, keyboard and status, but initially only one direct HDMI capture input. No DDR3 dependency in the baseline. A physical MEGA65 keyboard and HDMI monitor attached to the chain master can be switched among available targets. A salvaged ATX PSU and one Arduino-controlled eight-channel relay board provide independent 12V DUT power. Reuse existing FPGA Ethernet and MEGA65 protocol code where practical.

Out of scope initially: SD card emulation, arbitrary USB peripherals, HDCP, high-resolution video, persistent recording on FPGA, elaborate security on a trusted isolated lab VLAN, watchdog as a mandatory feature, and a second simultaneous digital video receiver per supervisor. Do not require alterations to a DUT core to make basic controls work.

## 2. User stories and acceptance outcomes

| ID | Story | Acceptance outcome |
|---|---|---|

| US-06 | As a tester I can see and hear output without USB capture dongles. | Host reconstructs raw RGB888 lines and PCM audio; missing lines and audio are detected rather than silently accepted as correct. |

## 3. System topology

```
Linux host: daemon, m65, Vivado, video receiver, test scripts
   | Ethernet trunk / test VLANs           | USB serial
   |                                      +--- Arduino --- 8 relay channels
   +--- switch (initially Cisco 3750)              |          | 12V DUTs
        |          |          |          |          |          |
      Mimas 0 === Mimas 1 === Mimas 2 === Mimas 3    +--- ATX PS_ON# (optional)
      MASTER       two DUTs   two DUTs   two DUTs
      two DUTs
      | physical MEGA65 keyboard
      | HDMI monitor
      === wired point-to-point video/control chain
```

Two nodes/four DUTs initially, four nodes/eight DUTs maximum planned. Each Mimas uses an identical bitstream, hardware profile and logical per-DUT engines. Chain position is discovered, not a different bitstream. The master is the unit with no physically connected uplink neighbour; distinguish physical absence from a failed/untrained link where hardware permits. Explicit topology recovery or override may be needed. Keep node identity (stable physical ID) distinct from topology index (may change when recabled). Every supervisor communicates directly with Linux via its own Ethernet port; a chain fault must not disable remote JTAG, UART or local capture on surviving nodes. The wired chain is for shared monitor, keyboard and low-rate control, not the primary Ethernet transport. Optional future Ethernet video playback is not a baseline requirement.

## 4. Hardware baseline and inventory

Observed boards: full-size Mimas A7, USB Type-B, USB VID:PID 2a19:1009. This strongly suggests pre-V4, but does not establish exact revision, FPGA package, pinout or FTDI wiring. Older documentation identifies RTL8211E Ethernet; V4 changes to KSZ9031, USB-C, asynchronous USB FIFO, and direct Vivado JTAG. Obtain board photos, FPGA marking, jumper positions, schematic revision and vendor XDC before implementation. Do not use Mimas Mini or V4 constraints blindly. The published old connector table uses A/B naming that must be reconciled with the physical row/pair interpretation reported by the owner. No connector pin assignments are approved yet.

Resources intended: HDMI RX and TX, GbE PHY, expansion A/B differential-capable pins, six PMOD groups as reported by owner, physical buttons, segment display and eight green LEDs. DP RX/TX, RGB LED and DDR3 are optional/verify. Do not assume a configurable bank voltage or a particular RGB LED is present. Check actual 5V external input and power selector; do not feed an unverified header or tie independent supplies together.

## 5. Power and electrical safety

**Agreed:** salvaged ATX supplies; Mimas on main 5V if board supports it, acting as useful 5V load; DUTs on individually switched 12V. Arduino 5V logic controls Jaycar XC4418 eight-channel relay board (12V coil supply, 5V logic). Arduino preferably powered from 5VSB with controlled USB power arrangement to avoid tying host VBUS to ATX standby. Switch remains independently powered. Optional transistor/open-drain control of PS_ON# permits global recovery. Separate supervisor reset/power cycling is optional, not required.

Use normally-open power contacts, per-DUT appropriately sized fuses (3A illustrative for nominal 2A, verify inrush and cable rating), positive-side switching and common ground. Assess relay contact DC inrush, connector rating and PSU 12V capacity; stagger loads. Do not open mains PSU. Qualify old group-regulated PSUs with 0/1/all DUTs, both Mimas loads, relay coils, standby startup, abrupt load changes and 5V/12V rail limits. Add dummy load only if measurements require. Confirm active-high input and safe reset behaviour; pull control inputs to OFF before Arduino startup. Do not assume 3.3V directly drives XC4418 reliably. Optional future direct Mimas relay controller via appropriate level conversion.

Initial cables are direct, without series resistance: minimise back-power risk in VHDL/XDC (safe configuration/startup pin behaviour, no pulls, output enables gated by valid target power). This is mitigation, not electrical isolation; qualify both power directions before unattended use. Custom adapters shall add series resistance and appropriate protection, and may use RJ45/8P8C with twisted-pair cable for point-to-point links. Such ports must be clearly marked non-Ethernet and never plugged into network/PoE equipment; verify grounds, pair allocation and termination. Target 3.3V from keyboard/JTAG headers is a **sense signal**, not a supervisor supply. Use high-impedance sensing with suitable series resistor and a buffer/comparator with powered-off isolation where required; verify thresholds and absolute maximum ratings in both power directions. Disable pull-ups. A plain input does not prevent clamp current when its own FPGA is unpowered. Tri-state all target outputs when target power is absent; use partial-power-down-tolerant buffers (Ioff) when required, including keyboard, JTAG, UART and HDMI sideband. Keep desired keyboard state internally across target power cycles. Ground connections must remain present during power cycling. Measure residual voltage when off; verify no unintended power via JTAG/keyboard/USB/HDMI. Never bridge VCCIO supply pins between boards merely because they are nominally equal.

Arduino interface proposed: line-oriented USB serial commands `STATUS`, `POWER <0..7> <0|1>`, `CYCLE <id> <ms>`, `ALL OFF`, optional `PSU ON/OFF`; return actual output latch state, errors and command IDs. Linux daemon serialises operations and maps DUT stable ID to relay channel. Explicit on/off is idempotent; cycle commands need duplicate protection. Optional master-to-Arduino UART later, with 5V/3.3V level conversion. No mandatory FPGA watchdog; safe startup, external recovery and reporting still required.

## 6. DUT cables and connector allocation

**Agreed:** maximise straight-through/keyed IDC harnesses, preferably coherent 2x6 blocks or 2x4 + 2x2 per function, using PMOD-like groups at the end of A/B rows. Avoid bespoke crossovers where possible. Target cable pinout follows real MEGA65 revision or HewnWeb header rather than guessing. Proposed signal budget per target: TCK/TMS/TDI/TDO, serial RX/TX, three keyboard protocol signals (verify directions), keyboard and JTAG voltage sense, optional power/reset contacts and DONE/INIT_B/PROGRAM_B. Physical keyboard host needs power and signals of its own; do not steal DUT supply. Optional features must carry validity flags; MEGA65 DONE/INIT_B may not be conveniently exposed.

Create a pin allocation worksheet with connector/pin, FPGA ball, bank, VCCO, direction, electrical standard, associated ground, DUT connector/pin, and optional feature conflicts. Check PMOD supply and ground pin orientation independently. Reserve enough pins for chain links and clock-capable inputs. If power/reset contacts are not needed initially leave unpopulated, not shorted. Use twisted signal/ground for JTAG and UART on long leads, reduce TCK, source series damping as measured, short stubs and adequate return conductors. For later cable assemblies use Cat6/Cat6A-style twisted pairs with keyed IDC transitions (not Ethernet-compatible connectors unless clearly labelled). Record maximum verified cable length rather than claiming a theoretical limit. Mechanical arrangement of MEGA65 boards remains owner work.

## 7. Wired supervisor chain

Goal: each adjacent unit connected by a simple straight cable between an A-side group and B-side group (or A-A/B-B if validated), with 3.3V VCCIO preferred for safety and common wiring. Owner reports differential pairs along each row and PMOD groups at the far end; old vendor naming must be mapped to actual pins. The 40-way IDC concept is a wiring goal, not a final pinout. A single row may need a custom cable/connector rather than a conventional 2x20 IDC. Include ground return pins; never route two outputs together. Supply pins not connected. Key connectors or detect/reject unsupported orientation; polarity tolerance means P/N inversion within pairs, not arbitrary pin reversal, supply swaps or unknown lane order.

### 7.1 Transport choices (review)

| Option | Logical lanes | Assessment |
|---|---|---|
| Parallel RGB888 + DE/HS/VS + clock, SDR 27MHz | 28 signals | Simple but pin hungry; usable if actual row provides enough single-ended signals and grounds. |
| 14 data/control lanes DDR at 27MHz + forwarded clock + audio | 16 signals | Preferred starting candidate; 28 bits/pixel including spare control; modest timing and BRAM cost. |
| 3 lanes, 10-bit TMDS symbols, 135MHz DDR + forwarded clock | 4 data/clock lanes plus control | Preserves HDMI data islands/audio/control, but needs proper symbol alignment, IO constraints and HDMI reconstruction; more risk. |
| Native LVDS at 2.5V | Depends on packing | Strong electrical option but conflicts with preferred 3.3V bank; only if bank mapping and jumper/safety permit. |
| External differential line drivers/receivers | Depends on packing | Allows 3.3V FPGA logic and real differential cable signalling; extra parts and board work. |

At 27MHz DDR, a lane carries 54Mb/s; 135MHz DDR carries 270Mb/s, enough for one TMDS lane. These are bit-rate calculations, not a verified cable timing budget. Native LVDS_25 output on Artix-7 HR banks requires 2.5V VCCO. TMDS_33 exists but has specific termination/common-mode requirements; do not treat as general LVDS. Complementary LVCMOS signals on pairs are another possibility only after checking timing, drive, termination and simultaneous switching; not a standards-compliant differential interface. Raw HDMI symbol forwarding is attractive for audio preservation, but do not require CDR on every hop if a forwarded source-synchronous clock is available. Confirm clock-capable pin routing, MMCM/PLL lock and serializer feasibility in exact part/package. At 135MHz use proper source-synchronous constraints, not ordinary unconstrained fabric timing.

Proposed baseline candidate (implementer to compare fabric/timing cost against raw TMDS symbol transport): forward decoded video plus sync/DE, with a small separate low-speed bidirectional control link carrying keyboard, topology, selection, LED state and link status. Use training pattern and per-lane invert flags for differential polarity tolerance; handle clock inversion via training/phase adjustment. If simple single-ended pin assignment wins, pair-swap tolerance applies only to a defined paired encoding. Choose a framing word and link CRC for control; no complex reliable transport required, periodic complete state resynchronises. Use IOB DDR primitives and forwarded clock; clock centred in data eye: 90 degrees of the DDR clock is a reasonable initial phase (quarter period, half UI), verify actual timing/skew, not a universal rule. For SDR centre sampling is nominally half a period. Use scope/ILA and test patterns across actual cables.

### 7.2 Chain enumeration and routing

Master at one end; downstream neighbour discovery via control link; enumerate 1..N and report stable board IDs, capabilities and available video inputs. Use bounded hop count (max four), reject loops/conflicts, invalidate topology after link loss. Each link point-to-point; no multi-driver bus. Master sends independently selected video and keyboard source IDs and selection epochs downstream. Local UI normally moves them together, but independent selection is agreed. Master alone owns wired video source selection; management can request a selection through master, not enable competing sources directly. Intermediate nodes forward video from downstream or insert local selected video; only one selected stream per direction towards master. Use explicit valid/idle state; no source drives until selected and stable. Local capture to Ethernet independent of routed output. For physical keyboard route bitmap downstream and selected target LED/status upstream. If chain supports bidirectional data, use separate lanes or explicit turnaround with no contention.

Display selection is logical target 0..7, not just supervisor 0..3. Initially only one of two targets per supervisor has HDMI; unavailable targets may still be selected for keyboard/JTAG, with monitor blank/status. Optionally use Kramer input mapping to make both selectable sequentially. Master eight green LEDs map to target index (one-hot selection; optional blink for unavailable/video unlocked). Segment display proposed `n oF m` using abbreviated/sequential display if digits insufficient, showing position and total supervisors. Other LEDs/RGB if fitted indicate keyboard ownership/colour; exact encoding and keyboard LED override/preservation require review. Local buttons select previous/next and auto-cycle, with debounce. Configurable dwell and skip unavailable sources.

### 7.3 Switching and timing

Wait for end of current frame, then blank output, avoid generating partial active rasters; select and lock new source, wait for next valid full frame boundary and resume. If source clock changes, use safe clock switching or separate clock mux/PLL reset and allow monitor resync; do not combinatorially mux unrelated clocks. Holding HS/VS at defined inactive levels while blanking is acceptable for initial mode changes but monitor may lose lock. Time out if current/next source absent. Regenerate native timing; optional continuous fallback black mode if easy. Audio must mute during change, reset packet/FIFO state and resume only for selected source. For decoded-video chain, reserve one additional source-synchronous serial data pin at 27MHz for digital stereo audio, with simple framing, sample-valid/rate metadata and resynchronisation; 27Mb/s easily accommodates stereo PCM (48kHz x 2 x 24 = 2.304Mb/s). Clock crossing and HDMI audio regeneration still require validation; video-only forwarding is insufficient for full audio pass-through. Raw TMDS symbol forwarding could instead carry audio and ancillary packets, subject to feasibility.

### Serial audio lane clarification (v0.3)

If decoded DVGA is selected, use one additional data pin clocked by the shared forwarded video clock. Conventional I2S uses separate bit clock, word select and data signals; an I2S-like single-data-lane format can instead embed framing/channel identification and sample-valid information, using the existing clock. PDM and S/PDIF are other single-signal concepts, but neither is mandated. Proposed baseline: framed PCM with sample counter, rate/format metadata and discontinuity indication; preserve sample timing through an elastic FIFO and regenerate HDMI audio clocking. At 27MHz SDR there is ample capacity for stereo PCM. Implementation LLM chooses simple framing and clock-domain strategy; no DDR3 needed.

## 8. Ethernet model and wire conventions

**Agreed:** two distinct MAC addresses and two IP addresses per Mimas, one per DUT; single physical PHY. Same service port numbers on every logical DUT, superseding unit-encoded port scheme. Stable locally administered unicast MACs provisioned uniquely; static IPs initially, configurable via management. ARP replies for both; support IPv4 unicast RX and broadcast video/telemetry TX. Broadcast destination configurable later. Dedicated test VLAN or isolated switch, configurable on host; initial Cisco 3750, fanless TP-Link later. DUT VLANs may be isolated separately; supervisor VLAN need not mirror DUT VLAN. No Internet exposure; remote JTAG and power are privileged. Tagged VLAN support in DUT cores optional, not a substitute for trusted isolation where malfunctioning cores matter.

Agreed common UDP port range 65xx, with destination IP disambiguating DUT. Proposed assignments: 6500 management, 6501 heartbeat, 6502 keyboard, 6503 UART, 6504 raster, 6505 audio, 6506 power proxy if desired, 6507 UDP JTAG. Individual assignments remain reviewable. XVC TCP 2542 on each IP. Use standard XVC without modification. All custom packets use a compact version/type/length header, unsigned multi-byte values network byte order (except XVC standard), fixed layouts where possible. No native C struct padding; explicit offsets. Include boot/session ID and sequence/counters as relevant. Reject truncated/oversized/version-invalid datagrams and incorrect IP/MAC/target. Broadcast RX configuration commands disabled unless explicitly provisioned; host daemon is sole normal writer. FPGA can compute IPv4 header checksum, Ethernet FCS and preferably UDP checksum; IPv4 zero UDP checksum optional if agreed. No IP fragmentation in baseline. ARP/ICMP support limited to requirements; no DHCP requirement. Avoid TCP implementation for custom services; XVC is the exception and may be proxied on Linux.

**MTU:** one 720-pixel RGB888 line = 2160 bytes + protocol/IP/UDP headers; Ethernet payload roughly 2220 bytes, thus jumbo support required on switch, NIC and FPGA MAC. Jumbo frames are agreed; configure MTU 9000 where supported and validate exact Cisco model. Fallback if impossible: split raster into two offset-tagged datagrams, not IP fragmentation. Keep this fallback optional. **Agreed:** raster packets have absolute priority at packet boundaries over UART, JTAG, heartbeat, audio and management traffic. Ethernet cannot interrupt a frame already on the wire; admission of lower-priority packets must therefore respect available raster-ring headroom, including preamble, FCS and inter-frame gap. Prefer a bounded raster packet ring over precise next-raster prediction. Bound lower-priority frame sizes or defer when headroom is insufficient; coalesce telemetry and count deferrals/drops. No full-frame video buffering or DDR3. Existing small line/CDC buffers are permitted; if literal streaming without line buffers is attempted, verify MAC underflow and header availability. Never stall the source; count unavoidable overflow. VLAN broadcast scope matters: all nodes' broadcasts replicate to every recipient port. Four simultaneous 500+Mb/s streams cannot converge on one 1GbE host or peer port; capture enable/selection per DUT and configurable destinations are essential. Ethernet video broadcast is OFF by default and explicitly enabled per DUT by management. Enable only needed sources, or use separate VLANs/NICs/multigig uplink later. Wired video routing is independent of Ethernet capture enablement and is controlled by the chain master. Wired chain keeps display traffic off Ethernet. Test saturated and unsaturated behaviour.

## 9. Video and audio capture

**Agreed:** one direct HDMI capture per Mimas initially, second DP input an investigation. No full-frame buffer or DDR3 required for capture or wired native pass-through. Decode HDMI active pixels and timing, preserve full RGB888 first. One UDP datagram per raster (including blanking rasters if enabled), raster and frame numbers. Use a small asynchronous FIFO feeding a nominal 16KiB BRAM packet ring in the Ethernet TX clock domain. At 720x576/50 or 720x480/60 active RGB888 rate about 498Mb/s; full 27MHz pixel stream 648Mb/s; actual Ethernet overhead and blank metadata added. Active line burst must be serviced before buffers fill, regardless of average. Use the async FIFO for clock crossing and pixel/raster markers, optionally a ninth bit marking end of raster on a byte-wide stream (or a wider pixel FIFO with equivalent flags). The FIFO must sustain 81MB/s active RGB888 production. Assemble packets in the TX-clock ring with a write pointer, committed pointer or descriptor queue, and read pointer; publish a packet only after all bytes and length are available. Reserve capacity before starting a raster, handle wrap, never overwrite unread data, and discard a complete raster on overflow with a counter and sequence gap. A nominal 16KiB ring holds roughly seven 2.2KiB raster packets; 16KiB of byte data requires about four BRAM36 by capacity, with descriptor/CDC storage additional. A 9-bit storage geometry may change mapping. Lower-priority packets can finish in flight; raster wins at every subsequent packet boundary. Avoid full-frame storage and source backpressure. RLE may use separate line scratch buffers if needed.

Proposed raster header after common header: frame u32, line u16, total pixels u16, active start/count u16 each, HS assert/deassert positions u16 each, flags (VS level/polarity, HS polarity, DE validity, frame boundary), encoding u8, payload count u16; UART RX sequence u32 and latest sixteen RX bytes (zero-filled history, no valid-count field); add pixel clock Hz and total lines in heartbeat or frame descriptor. Define positions relative to pixel zero, half-open intervals, handling wrap. Send blanking lines with zero pixel payload to preserve timing. VS transition within a line, interlacing, half-lines and unusual timing require explicit capability/metadata or mark unsupported; do not claim reconstruction from only per-line VS bit for all modes. Frame counter wraps modulo 2^32. UART fast-path metadata is included even in blanking raster packets when emitted; its sequence uses exactly the same byte-counter convention as UART snapshots. Receiver merges both histories, never emits duplicate bytes, and uses the periodic 512-byte history to repair gaps. Receiver checks missing/duplicate/out-of-order lines and invalid frames; host may display stale/diagnostic pixels but CI must reject incomplete capture. Native HDMI output uses source timing from local or chain, not UDP arrival timing. Network playback later requires elastic buffering, clock adaptation and possibly DDR3; cannot guarantee jitter-free display with no buffer.

RLE24 optional: repeat tuples of count u8 (1..255) + RGB888; split longer runs, no ambiguous escape; only send RLE if strictly smaller than raw. Compare by counting as line arrives or encoding to separate bounded scratch buffer; abort candidate on reaching raw size. Raw fallback always available. Do not assume one ping-pong pair alone suffices for simultaneous encode/write/read; use second port or candidate BRAM and cycle budget. Preserve exact RGB. Further encoding, RTSP/RTP considered after crude receiver; RTSP is session/control, not a video codec. Host gateway can expose RTP/RTSP (e.g. raw RFC4175 or software encoded) without FPGA complexity.

Audio: decode HDMI audio data islands (TERC4, packet checks, audio clock recovery ACR N/CTS, sample layout) and send PCM with sample counter, frame association, sample rate, channel count, format and discontinuity. At 48kHz stereo 16-bit, 50Hz frame holds 960 samples/channel or 3840 bytes; 60Hz about 3200 bytes, fits one jumbo or multiple ordinary datagrams. To group per video frame needs a small FIFO/BRAM, not DDR3; alternatively emit bounded chunks during frame, flush at boundary. Support audio with no video lock only if receiver permits. Preserve source rate/validity; do not assume 48kHz or 16-bit always. Baseline HDMI RX/TX examples may be DVI-only, so audio needs separate validation. Full pass-through requires HDMI audio packet regeneration or raw symbol forwarding. HDCP excluded. EDID/HPD: supervisor input behaves as sink and serves programmable EDID presets or host-supplied bytes; supervisor output behaves as source, reads monitor EDID and detects HPD. Host can override output mode; do not confuse input EDID emulation with output DDC direction. Check DDC voltage tolerance and actual board routing; open-drain only. Expose lock, timings, audio rate, HPD and EDID status in heartbeat. No assumed access to every signal until schematic verified.

## 10. Keyboard and physical arbitration

Reuse actual MEGA65 keyboard HDL for supported mainboard/keyboard revisions. Verify bitmap size/order, polarity and scan timing. Two independent keyboard device FSMs plus one physical keyboard host FSM per supervisor. UDP sends complete bitmap to destination DUT IP; allow setting it while target is off. Keep desired UDP bitmap, physical bitmap, effective presented bitmap and ownership independently. Report all relevant states in heartbeat.

**Agreed ownership:** an actual physical key press transfers selected DUT to physical state, including subsequent releases. A UDP bitmap that differs from the previously stored UDP bitmap transfers ownership back to UDP; identical retransmissions do not. Physical release alone does not steal ownership. Agreed: on changing selection or losing the physical keyboard route, old DUT immediately presents its most recent UDP bitmap, with no residual physical holds. Management selects held-key behaviour on assignment: REQUIRE_FRESH_PRESS (proposed default: remain under UDP ownership until a new physical key-down transition) or ACCEPT_HELD (immediately claim physical ownership if any key is already held). Resolve simultaneous events deterministically (proposed UDP wins). Chain carries full keyboard snapshots and selection epoch; reject stale routes and clear physical state on link loss, without expiring deliberate scripted holds. Explicit force-owner/all-up management optional. Return effective bitmap and ownership in heartbeat. Keyboard LED colour indicates selected target, preserve target status LEDs where practical; verify actual keyboard models. Master eight green LEDs show selected DUT (agreed: steady for video, blinking for keyboard when selections differ), RGB LED if present shows corresponding colour, segment display shows chain position/count. No USB keyboard dependency.

## 11. UART transport

Two independent UDP UART bridges. Configurable baud/framing; initial 2Mbaud candidate subject to target monitor support. Periodic snapshot includes latest 512 bytes RX and 128 bytes actually transmitted, TX free count, valid lengths, cumulative RX/TX accepted/TX emitted byte counters, boot ID, snapshot sequence, framing/overflow/rejected packet counts. Histories oldest-to-newest, zero-pad unused bytes; counters identify absolute byte positions. Host recovers overlap and detects unrecoverable gaps. No FPGA retransmission. Agreed default 1kHz snapshots. At 2Mbaud 8N1, 200kB/s, 512 bytes covers 2.56ms (2.56 snapshot intervals; one consecutive lost snapshot can be repaired at sustained maximum rate). Payload histories total 640kB/s per UART, 1.28MB/s for two before headers. Include a 32-bit cumulative RX byte sequence (next byte offset), and independent snapshot sequence; latest N actual bytes occupy offsets [RX_seq-N,RX_seq) modulo 2^32. Raster packets carry the same RX sequence and latest sixteen bytes for low-latency delivery; at 200kB/s up to 13 bytes arrive per 64us PAL line, so sixteen bytes cover one normal PAL line at maximum baud, but missing packets or longer lines still require snapshot repair. At 1Mbaud, approximately 6.4 bytes arrive per line. Raster piggybacking requires Ethernet video streaming to be enabled; the independent fast UART option below does not. Host merges overlapping histories and releases only contiguous data, using snapshots to recover missing bytes. Boot ID disambiguates restart; compare offsets modulo 2^32 within half-range. Disable unused streams. Raster history is initialised to all zeroes and has no valid-count field. A UART TX request may carry a CLEAR_RX_HISTORY flag; clear both raster and snapshot RX histories to zero without resetting the cumulative RX sequence or TX offsets. Proposed: accept this flag only with a valid sequenced request and make clear-only requests idempotent using a separate command ID (or an equivalent management generation); report a history-clear generation and RX sequence at clear in normal UART telemetry so the host can distinguish padding from real zero bytes and detect intentionally discarded history. Before the first byte after boot, history is padding; host uses boot identity and cumulative sequence. Define ordering of clear versus simultaneous RX and snapshot creation; do not emit padding as serial data.

**Agreed independent fast UART mode:** management enables/disables per DUT. On newly received UART byte, make a snapshot immediately due (reset countdown to zero), subject to at least 100us between snapshot dispatches. If within that interval, latch a pending request and send at the earliest permitted time; do not lose the last byte of a burst. Retain 1ms periodic idle reporting; restart periodic deadline after dispatch. Coalesce RX events and feedback requests into one snapshot. Default fast mode off is proposed. A 10kHz ceiling costs 6.4MB/s of history payload per UART, 12.8MB/s for both, before overhead; rate-limit and count deferred dispatches. Fast mode does not depend on video. Ethernet scheduling latency and a currently transmitting jumbo frame may delay actual wire transmission.

Host-to-DUT UDP packet sends bytes to TX ring, up to bounded payload. Agreed expected TX accepted-byte offset is mandatory; compare to current next-expected TX offset before enqueue. Proposed all-or-nothing admission; drop without enqueue if insufficient free space or offset mismatch, increment appropriate rejection counter. Every UART snapshot explicitly reports next expected TX offset, TX free space and emitted offset. Offset mismatch triggers high-priority snapshot request (subject to proposed shared 100us minimum spacing/coalescing); ring-full may use same feedback. Host retries only unaccepted bytes, never already accepted commands. Duplicate packets must not enqueue twice; stale/reordered packets are rejected. TX acceptance is not proof of physical transmission. Do not blindly retry arbitrary serial commands. Host offers PTY/raw TCP adapter for old tools and m65 backend. Test wraparound, identical data, packet gaps, ring full, boot ID change, baud changes. Keep outputs safe when DUT off.

## 12. JTAG and supervisor programming

Two independent hardware shift engines. Standard XVC 1.0 TCP service on each logical IP, same port: `getinfo:` returns `xvcServer_v1.0:<maxbits>\n`; `settck:` accepts/returns 32-bit little-endian period; `shift:` accepts 32-bit little-endian bit count then ceil(n/8) TMS bytes and TDI bytes, returns TDO bytes, LSB first. Follow AMD reference, edge timing and final partial byte. Start conservative TCK, configurable for cable. Exclusive ownership per DUT; release on close; reject unpowered shifts. TCP parser handles segmentation/coalescing. Agreed: Linux XVC-to-UDP proxy is acceptable and is the preferred low-fabric baseline candidate; native FPGA TCP is optional if reuse of HewnWeb TCP is simpler. Proxy exposes independently addressable standard XVC endpoints and maps them to bounded UDP JTAG transactions. Each DUT needs a transaction ID, session/boot identity, cached most recent completed response and duplicate protection; retry must never clock the same vector twice. Stop-and-wait per DUT keeps FPGA state bounded. **Agreed:** JTAG requests carry sequence numbers and requested TCK and reporting frequency (explicit units and supported bounds to be defined). Each status/result reports next expected transaction sequence, active/completed sequence, busy, available capacity, actual TCK/report period and error flags. Reject unexpected sequences without clocking; request high-priority feedback on mismatch, including cached result for duplicate completed request. Duplicate in-flight requests report busy without restarting. Report periodically while active at configured rate and promptly on completion/rejection; proposed bounded rate/coalescing protects video. Configuration changes take effect between transactions; retries must not change an accepted vector or its timing. JTAG resembles UART in sequenced admission and feedback, but is synchronous: every TMS/TDI bit must produce exactly one corresponding TDO bit, and TAP state makes replay unsafe. Retain complete bounded TDO result until next valid transaction is accepted; host must retrieve it before advancing. No raster JTAG piggyback. Proposed initial stop-and-wait rather than streaming history, with optional pipelining only if performance warrants. A reset or uncertain session aborts the operation rather than blindly replaying shifts. Extend m65 with network selection, XVC and UDP UART/keyboard backends.

Bootstrap: inspect old USB interface and schematic. Vendor recognizes VID:PID 2a19:1009 and Tenagra programming. V4 explicitly adds direct FTDI channel A JTAG, so adding USB ID to m65 alone is not proven sufficient. Run `lsusb -v -d 2a19:1009`, inspect driver bindings and FTDI channel routing; try documented Tenagra method or external JTAG header to obtain IDCODE. Older Tenagra XVC bridge can support Vivado. Do not modify EEPROM or flash until SRAM programming works. Determine whether m65/openFPGALoader patch is appropriate; record recovery procedure and known-good image.

### 12.1 Exact bit counts and transaction chaining

**Agreed:** each UDP request represents one complete bounded shift transaction, with an explicit bit count (proposed u32), two vectors each ceil(bit_count/8) bytes, LSB first, and a TDO result of the same rounded byte length. Ignore unused input padding bits and zero unused result bits. Reject zero or excessive lengths and malformed vector sizes without any clock edges. Proposed maximum 8192 bits initially (2048 bytes combined input vectors, 1024 bytes result), adjustable to BRAM/MTU and advertised by the XVC proxy. No IP fragmentation. The count includes every TCK cycle including TAP navigation. Execute exactly N clocks, with TMS/TDI stable before rising edge, TDO sampled at the appropriate rising edge, and finish with TCK low. Preserve TMS/TDI and TAP state between requests; no implicit TAP reset, idle clocks or transition. The next vector can start in SHIFT-DR or any other TAP state. Clock may remain stopped indefinitely for ordinary TAP operations; respect device-specific programming timing requirements. USB FTDI MPSSE similarly clocks bounded byte/bit commands and pauses between commands; see FTDI AN_108 and AN_135. XVC proxy may split longer logical requests into bounded shifts with no extra edges, but should advertise the supported maximum to clients. On loss of target power or session state, report abort and require explicit recovery rather than replay. Raster priority affects network reporting only, not an admitted JTAG shift's clock generation. Test non-byte-aligned lengths, segmentation across every TAP state, lost responses, duplicate commands, and exact TCK edge counts.

## 13. Management and heartbeat

Per-DUT UDP broadcast roughly once per video frame, fallback nominal 50Hz timer even with no video/target power. Include protocol/build ID, stable board ID, boot ID, topology index/count, DUT index, capabilities, selected target, keyboard ownership/effective/requested bitmaps, target power sense/validity, relay state if known, optional DONE/INIT_B and validity, UART counters, JTAG busy, video lock/pixel clock/geometry/frame number, HDMI HPD/EDID/audio status, drop/link error counts and configuration generation. Master heartbeats additionally carry the entire raw physical keyboard bitmap, independent of selection and ownership, with validity and change counter. Host daemon can implement arbitrary hotkeys; a periodic bitmap alone may miss a press/release between reports, so **Agreed:** request expedited master heartbeat on every physical keyboard bitmap change; raster priority still applies. Coalesce pending reports, retain a change counter; if every short transition must be observable despite coalescing/loss, an event FIFO is a future option. Board-level fields can repeat per DUT. Versioned bounded layout; validity bits for MEGA65 vs HewnWeb. Host detects gaps and reboot. No mandatory watchdog: state snapshots allow recovery from packet loss, not a wedged FPGA.

Management sets whole values rather than toggles: MAC/IP, port/destination, baud, independent fast UART enable, capture enable, held-key assignment policy, ownership override, EDID bytes/preset, HPD, independent keyboard and display source IDs, coupled-selection convenience mode (default), cycle/dwell, link configuration. Fixed command IDs and bounded payload; reject malformed. Proposed generation echoed in heartbeat. Changing IP/MAC requires known recovery (announce new identity/default reset). Initially volatile settings restored by host. Power commands go via daemon/Arduino; do not imply FPGA knows relay state unless supplied.

## 14. Kramer and alternate inputs

Existing VP-728 has two VGA/UXGA and two HDMI inputs, HDMI output, RS-232 control (9600 8N1); no Ethernet, unlike VP-729/731. Use proper RS-232 transceiver. Earlier command candidates Y104/Y105 VGA, Y106/Y107 HDMI, CR terminator, Y10 query: verify against manual/unit. One per Mimas permits sequential capture of both DUTs, not simultaneous. Scaler alters timings/colour/latency, so mark indirect capture unsuitable for native pixel-exact tests. Daemon or optional FPGA UART controls selection and waits for lock. DP capture open: inspect GTP/SelectIO routing, AUX/HPD, reference clocks, available DP sink IP/resource cost. DP is packetised; passive DP-to-HDMI adapters cannot be reversed; 270Mb/s TMDS below typical GTP operating range, electrical compatibility unproven. Active conversion still needs DP sink. Do not block baseline on DP.
